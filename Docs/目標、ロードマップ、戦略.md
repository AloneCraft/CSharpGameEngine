## 2. 最終的に何をやろうとしているのか（決定）

### 2.1 目標

> **C# と Visual Studio だけで、テキストを正本にして、量子から銀河までの大きさの世界を決定的に動かす 3D ゲームを、Unity や UE より少ないコードで作れるエンジン。**

この一文は、これまでの決定から次の 4 本を取り出したものである。迷ったときは、この 4 本に効くかどうかで判断する。

| 柱 | 中身 | 既存の根拠 |
|---|---|---|
| 1. 書く量が最小 | Component と System だけ。Query、ループ、起動処理、順序の大半は生成器が決める。間違いはコンパイルエラーで知らせる | ADR-0033、ADR-0077 |
| 2. テキストが正本 | C#、JSON、元の素材だけを Git に入れる。生成物はいつでも作り直せる。CLI だけで全工程が動く | ADR-0002、ADR-0070 |
| 3. 全スケールで決定的 | 固定小数点、階層座標、対数深度。同じ入力から同じ結果 | ADR-0063、ADR-0084、ADR-0086 |
| 4. 機械が検証できる | 画面なしで実行し、判定基準で合否を出す。未確認を成功と書かない | ADR-0051、ADR-0057 |

柱 2 と柱 4 は、AI エージェントと一緒にゲームを作るための条件でもある（シーンを文字で読み書きでき、結果を自分で確かめられる）。このエンジン自体がその作り方で出来ている。

### 2.2 誰のためか
- 第一の利用者は所有者自身。自分のゲームをこのエンジンで作る。
- 次は、C# を書ける個人と小さなチーム。Windows PC 向けの 3D ゲーム。AI エージェントに実装を任せる作り方をする人。
- 対象にしないのは、アーティスト主体のチーム、モバイルと家庭用ゲーム機が必須の案件、ノードだけで作りたい人。

### 2.3 目指さないもの
- Unity や UE の代わりになる汎用エンジン。
- UE と同じ見た目（Nanite、ハードウェア レイトレーシング、Lumen の Epic 設定）。
- 科学計算の道具。量子と確率の Domain はゲームの表現としてだけ扱う。
- 独立したエディター アプリ。編集は Visual Studio の中だけ。

### 2.4 達成の判定
1. 所有者が、リポジトリの外で、SDK パッケージと VSIX だけを使ってゲームを 1 本完成させ、配布した。
2. そのゲームが柱 3 を使っている（1 つのシーンの中で、地表の 1 mm と軌道の距離を同じ座標で扱う）。
3. 別の PC で、VSIX を入れてからテンプレートが動くまでを、文書だけで再現できた。
4. 同じ入力の再実行で状態のハッシュが一致する（すでに Stage がある。ゲーム本体でも確認する）。

## 3. ロードマップ（決定）

期日は置かない。段階ごとの出口条件で管理する。新しいマイルストーンを切るときは、どの段階の出口条件に効くかを文書の冒頭に書く。効かないものは段階 D へ送る。

### 段階 A — 閉じる
広げるのを止め、開いたままの制作の一巡を閉じる。

| 作業 | 対応 |
|---|---|
| 制作の一巡を実 VS で受け入れる | M0128、F-L8-035、F-L8-036 |
| モデル取り込みの残りを、要るものと送るものに分ける | M0114 |
| 描画の L4 化を、フレーム計画の移行まで終える | M0120 の段階 1 まで |
| VSIX のリリース証跡 | F-L8-029 |

出口条件:
- 別の PC（または同等の隔離環境）で、VSIX の導入 → 新規プロジェクト → 素材追加 → シーン編集 → ビルド → 自己完結の配布物 → 実行が、実 VS で通る。
- PartiallyImplemented の 11 件が、Implemented になるか、理由つきで Deferred になっている。
- `Roadmap.md` と `Architecture.md` の冒頭に積んだ経過報告を、マイルストーン文書へ移して削る。

### 段階 B — 1 本作る
柱 3 を使う小さなゲームを、リポジトリの外で作る。エンジンの修正は、そのゲームが要るものを優先する。

| 作業 | 対応 |
|---|---|
| 全スケール物理 | M0122（ゲームが地表と軌道の両方で物理を使うため） |
| ゲーム本体（地表から軌道まで続く小さな作品） | 新規。素材は自作か、条件が明確なもの |
| 足りない基本機能（セーブの画面、設定、音の調整など） | ゲームで困った順 |
| ユーザー向けの手引き | 今の文書は開発者向け。作りながら書く |

出口条件: 2.4 の 1・2・4 を満たす。

### 段階 C — 公開できる形にする（1.0）

| 作業 | 内容 |
|---|---|
| テンプレートの素材 | UE 由来の内容を、自作か条件が明確なものへ差し替える（6.2） |
| API の凍結 | 段階 B で変えたくなった所を全部壊してから凍結する（5 章） |
| 互換性の規則を機械で守る | 公開 API の差分検査、移行ツールの試験 |
| ライセンスと配布先 | エンジンのライセンスを決め、NuGet と VS Marketplace に出す |

出口条件: 2.4 の 3 を満たし、5 章の「1.0 以降」の規則が有効になる。

### 段階 D — 広げる
実際のゲームが要求した順に足す。要求が無いものは作らない。

- 描画: Forward と Forward+ の作り直し、Deferred と Deferred+（M0120 の残り、M0121）。
- 物理: 契約とソルバーの分離、Joint、Ragdoll、動的同士の CCD、並列、Rollback。
- Simulation: 変形、流体、N 体。
- 2 つ目のプラットフォーム。L0 の境界は保ってあるので、バックエンドの追加で済む構造にしてある。

### 順序を変えた点
- M0121（Deferred 系）は 1.0 の後へ送る。ADR-0085 は取り消さない。実施の時期だけを変える。
- M0122（全スケール物理）は前へ出す。柱 3 の中心で、段階 B のゲームが使う。
- M0120 は L4 化までを段階 A に入れ、Forward 系の作り直しは段階 D へ送る。

## 4. 何を妥協するべきか（決定）

### 4.1 捨てる・後へ送る

| 対象 | 決定 | 理由 |
|---|---|---|
| プラットフォーム | 1.0 まで Windows x64 と Direct3D 12 だけ | 検証の組み合わせを増やさない |
| エディター | Visual Studio だけ。Rider と VS Code での編集は対象外 | 独立エディターを作る費用を、エンジン本体へ回す |
| UE との見た目の一致 | テンプレートの移植で終わりにする。残る差は文書に残して閉じない | 目標は UE の複製ではない。M0111 と M0112 に差を記録済み |
| 描画パス | 1.0 は現行の 1 系統。4 パスは段階 D | 4 パスの一致検証は高価で、ゲーム 1 本には不要 |
| 数値設定 | 保証を 3 段に分ける（下の表） | 固定 12 設定 + Float + Double の全部に同じ保証はできない |
| 決定性の範囲 | 同じビルド、同じ数値設定、CPU の経路だけ。版をまたぐ再生と GPU の結果は保証しない | 版ごとの一致を約束すると、ソルバーを直せなくなる |
| Simulation の将来機能 25 件 | 1.0 まで着手しない。カタログの項目は残す | ゲームが要求していない |
| ネットワーク対戦 | 1.0 の範囲外 | Rollback（F-L5-011）が未着手。決定性は土台として残る |
| UI | `ScreenText` と `ScreenImage` で足りる範囲。UI の仕組みは作らない | 段階 B のゲームが要る分だけ足す |
| 実機の検証 | WARP を必須、実 GPU は所有者の PC だけ | 実機の表を広げる手段が無い |
| 性能 | 個人制作の規模で 60 Hz。大群衆や大量の剛体は狙わない | Q64.64 は float より遅い。正しさを先に取る |
| コードのホットリロード | しない。値の編集だけ即時 | 静的 Archetype と生成器の前提に反する |

数値設定の保証:

| 段 | 設定 | 保証 |
|---|---|---|
| 1 | Q64.64 + 対数深度（既定） | 全 Stage、決定性、全スケール |
| 2 | Double + 通常深度 | ビルド、テンプレートの実行、保存の読み書き。決定性と全スケールは保証しない |
| 3 | それ以外の固定幅と Float | ビルドと数値ライブラリの試験だけ。実験扱い |

### 4.2 妥協しないもの
- 層の依存方向。L0〜L6 は Roslyn と Visual Studio SDK を参照しない。
- 正本はテキストと元の素材。CLI だけで全工程が動く。
- 段 1 の決定性。
- 未実装、未確認、時間切れを成功と書かない。
- ユーザーに書かせる量を増やさない。機械が決められることを書かせない。

### 4.3 進め方の妥協
- 文書の台帳（`Implementation-Status.md` 約 495 KB、`Conformance.md` 約 584 KB）は維持費が高い。触った機能の項目だけを更新し、全体の書き直しはしない。冒頭の経過報告は段階 A で削る。
- 実 VS の手動確認は、段階の出口条件に入っているものだけ行う。途中の変更は自動試験と WARP で進める。

## 5. 後方互換性の戦略（決定）

### 5.1 前提
- **事実**: 並行リーダーを残さない方針がすでにある（`Roadmap.md`「Do not retain old APIs, readers, generated artifacts」、ADR-0070 §7）。一方で、シーン JSON は旧版を一括変換するツールがあり（`SceneJson.Cli upgrade`）、Snapshot v2、WorldCell v2、`.cgephyscache` スキーマ 3 は 1 つ前を読む。
- **仮説**: 外部の利用者はまだいない。
- **決定**: 1.0 までは、壊すことを恐れない期間として使う。互換のために残した名前（例: シーン JSON のための名前空間 `CSharpGameEngine.Runtime.Windows`）は、1.0 の前に一括変換で消す。

### 5.2 対象ごとの規則

| 対象 | 例 | 1.0 まで | 1.0 以降 |
|---|---|---|---|
| A. ユーザーが書いた資料 | シーン JSON、`.cgeasset`、`.cgepreview`、サイドカー、シェーダー グラフ、csproj の設定、プラグインのマニフェスト | 壊してよい。ただし変換ツールを同じ変更で出す。読み手は最新版だけ。旧版はビルド エラーで変換方法を示す | 1.0 以降のすべての版から最新へ、変換を連鎖で保つ。読み手は最新版だけ |
| B. ユーザーの C# | Component、System の引数の規則、属性、生成される API、診断 ID | 壊してよい。黙って意味を変えない。消した書き方は診断で知らせる | メジャー版でだけ壊す。1 つ前のマイナー版で警告し、アナライザーのコード修正を付ける |
| C. 作り直せる生成物 | シェーダー成果物、モデル成果物、`.cgenav`、`.cgefracture`、`.cgesdf`、キャッシュ | 互換なし。版か指紋が合わなければ拒否して作り直す | 同じ。旧版の読み手は作らない |
| D. 遊ぶ人のデータ | Snapshot（セーブ） | 保証しない | 容器の形式は、1.0 以降のすべての版を読む。Component の形の変更は、ゲームが移行を宣言する。宣言が無い型の不一致は拒否する |
| E. 決定性に縛られた記録 | 物理キャッシュの再生、リプレイ | 互換なし | 同じ。エンジンの版と数値設定が一致するときだけ再生する |
| F. 道具の間の通信 | プレビューのプロトコル、ブリッジの DTO、Stage の結果 JSON | VSIX は同梱した SDK と同じ版だけを扱う。違えば明示のエラー | VSIX は同じマイナー版の SDK を扱う。違えば更新を案内する |
| G. エンジン内部の API | アセンブリ間の呼び出し | 互換なし | 互換なし。SDK は 1 つの版で固めて配る |
| H. 土台 | .NET、Visual Studio、Windows | 最新の LTS の .NET と、対応する VS の 1 世代 | 同じ。LTS が替わるメジャー版で切り替える |

### 5.3 共通の規則
1. **壊すときは止める。** 旧形式を黙って読んで違う結果にしない。エラーにして、直し方を書く（SCENE206、NUM002、PLUGIN005 と同じ形）。
2. **変換は 1 方向、1 回。** 旧版を読む経路をランタイムと生成器に残さない。変換は CLI が行い、元の書式を保つ。
3. **互換は試験で守る。** A と D は、各版の見本を試験の入力に残し、最新版への変換と読み込みを毎回確かめる。
4. **版の付け方。** 最初の公開まで製品の版は 0.1.0 に固定し、壊す変更でも上げない。SDK パッケージは `0.1.0-dev.N`、VSIX は `0.1.0.N` として、中身を変えるたびに N を上げる（NuGet のキャッシュと VSIX の更新のため。ADR-0098 §5 規則 4）。公開した後は、A か B を壊したらマイナーを上げ、`CHANGELOG.md` に移行の手順を書く。
5. **プラグイン。** Runtime のソースは SDK の版に結び付く。マニフェストの `EngineVersion` の範囲で守る（ADR-0079）。規則は B と同じ。

### 5.4 生成器を持つことの利点
Component と System の書き方をエンジンのアナライザーが読んでいるので、B の変更に自動のコード修正を付けられる。Unity や UE では手で直す移行を、このエンジンでは機械に任せられる。1.0 以降の B の規則は、これを前提にしている。

## 6. 類似ソフト、アセットに対する優位性

比較相手の記述は 2026 年 6 月までの知識による。公開の前に確かめ直す。

### 6.1 エンジンとの比較

| 相手 | 相手の強み | このエンジンが勝てる点 | 負けている点 |
|---|---|---|---|
| Unity（GameObject と Entities） | 対応機種、アセット ストア、情報量 | ECS が後付けではない。GameObject と Entity の 2 つの世界とベイクの橋渡しが無い。最新の .NET と C# をそのまま使う。固定小数点と大スケールが標準 | 機種、素材、エディターの完成度、利用者の数 |
| Unreal Engine 5 | 見た目、大規模制作の道具、C++ の性能 | C# だけで書ける。Blueprint と C++ の二重が無い。資料がテキスト（UE はバイナリ）。決定的。UE のレベルと Blueprint の処理を読み出す道具がある | 見た目の上限、機種、制作の道具の広さ |
| Godot 4（C#） | 軽さ、テキストのシーン、無料、機種 | ECS とデータ指向が中心。シーンにスキーマがあり、ビルド時に検査する。決定的な物理と大スケールが標準（Godot は倍精度のビルドを自分で作る） | エディターの手軽さ、機種、利用者の数 |
| Stride、Flax | C# の独立エディター | Visual Studio の中で完結する。生成器による静的 ECS。全スケール | 独立エディターの機能、機種 |
| Bevy | ECS の設計、Rust | C# と Visual Studio。エディターと制作の一巡がある | ECS の柔軟さ（実行時に構成を変える） |

### 6.2 アセットやライブラリとの比較

| 相手 | 中身 | このエンジンの優位 | 相手の優位 |
|---|---|---|---|
| Photon Quantum | Unity 上の決定的 ECS（固定小数点）。対戦のための製品 | 固定小数点の幅が広い（Q64.64）。エンジン全体が同じ数値で、描画まで対数深度でつながる。ホスト エンジンとの二重管理が無い | ネットワーク対戦の完成度、実績 |
| C# の ECS ライブラリ（Arch、Friflo、DefaultEcs、LeoECS、Entitas、Svelto） | 実行時に Query を組む ECS | Query を書かない。間違いがコンパイル時に出る。描画、物理、エディターまで一体 | どのエンジンにも入る。実行時に構成を変えられる |
| 浮動原点や大世界のアセット | 原点をずらして float の誤差を避ける | 原点をずらさない。物理、音、描画が同じ座標を使う | 既存のプロジェクトへ足せる |
| 決定的な物理ライブラリ | 固定小数点の物理だけ | 物理、キャラクター、車両、破壊、ベイクが同じ tick と同じ数値で動く | 単体で使える |

### 6.3 まとめ
- **勝てる場所（決定）**: 「C# で書く」「テキストが正本」「決定的で大スケール」「機械が検証できる」の 4 つが同時に要る案件。この組み合わせを標準で持つ相手は、上の表には無い。
- **勝てない場所（事実）**: 対応機種、素材の市場、利用者と情報の量、制作の道具の広さ、見た目の上限。ここでは競わない。
- **未検証（仮説）**: 「書く量が少ない」は、同じ内容を Unity と UE で書いた行数と比べていない。「大スケールでも実用の速さ」は、他のエンジンと同じ場面で測っていない。段階 B で測る。

### 6.4 弱みと対処

| 弱み | 対処 |
|---|---|
| 作り手が 1 人（と AI） | 柱 4 を崩さない。検証が自動でなければ続かない |
| 出荷したゲームが無い | 段階 B |
| テンプレートが UE 由来の内容を含む（`THIRD_PARTY_NOTICES.md`）。UE の EULA は、エンジン コードを含まない製品の条件に「Starter Content をソース形式で含まない」を挙げている。公開の配布はできない見込み（仮説。法的な判断は所有者が [EULA](https://www.unrealengine.com/en-US/eula) で確かめる） | 段階 C で差し替える。それまで SDK と VSIX を公開の場所へ出さない |
| 利用者向けの文書が無い | 段階 B で書く |
| Visual Studio と Windows に縛られる | 受け入れる（4.1）。L0 と L8 の境界は保つ |
