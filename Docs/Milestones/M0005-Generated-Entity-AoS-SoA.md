# M0005: Generated Entity Source Generator(AoS / ECS SoA)の追加

## 目的
`[GenerateEntity(EntityGenerationSettings.Kind)]`属性を付けたpartial structから、`const`の
`EntityStorageKind`切り替え1つでAoS(Array of Structs)またはECS SoA(Struct of Arrays)の
物理ストレージ実装だけを生成するRoslyn Source Generator(`GenerateEntityGenerator`)を新規に
実装する。公開されるFacade(`Character`等)の型・コピー意味は両Backendで完全に同一とし、
生成コードにRuntime分岐を一切残さない。詳細な設計判断は
[[ADR-0024-Generated-Entity-AoS-SoA]]、仕様は[[Generated-Entity-Storage]]に記録した。

## 意図的に除外したこと

- 固定容量ページングによる物理的な複数Chunk生成(ユーザー確認済み、単一Chunk方式を採用)。
- AoSバックエンドでの異なる生成型間のストレージ共有(SoAのみ対応、見本互換のper-type store)。
- `[GenerateEntity]`の`UserGameProject`への実利用追加。`UserGameProject/Scene1.cs`が同じ
  `UserGameProject`名前空間に独自の`Entity`/`World`/`Archetype`語彙を宣言しており、
  `Program.cs`に既に`using World = CSharpGameEngine.Ecs.World;`という衝突回避エイリアスが
  ある状態に、同種の衝突リスクを新規に持ち込まなかった。実証は
  `CSharpGameEngine.CodeAnalysis.Tests`のend-to-endテストで担保した。
- `MoveAll`のような生成メソッド。プロンプト本文の「共通生成コード」セクションは要求しておらず
  (見本の`ICharacterGeneratedStorage`はデモ専用と明記)、代わりに`ChunkView`という
  バッチ基盤のみを生成する。
- 動的Add/Remove、Archetype Migration、Query/System基盤、Job Scheduler、自動並列化
  (ADR-0015と同じ非目標を継続)。
- `CSharpGameEngine.CodeAnalysis.Abstractions`の新規作成(3つ目のGeneratorだが、
  `GenerateEntity*`ファイル群と`EcsArchetype*`ファイル群の間で実際に共有できるロジックは
  今回確認できなかった。再検討トリガーはADR-0015の記載を継続する)。

## リバースエンジニアリングした挙動
- `GenerateEntityGenerator`は`ForAttributeWithMetadataName(
  "CSharpGameEngine.Generation.GenerateEntityAttribute", ...)`で対象構造体を検出し、
  `GenerateEntityAnalyzer.Analyze`が`ctx.Attributes[0].ConstructorArguments[0]`から
  `EntityStorageKind`の解決済み整数値を読み取る。ソース側が`EntityGenerationSettings.Kind`
  という`const`フィールド参照であっても、Roslynが属性バインディング時点で解決済みの値を
  返すことを実際のコンパイル・テストで確認した(手動での`SemanticModel.GetConstantValue()`
  呼び出しは不要だった)。
- 選択されなかったBackendの`AddSource`は実際に一度も呼ばれない
  (`GeneratorDriverRunResult.Results[0].GeneratedSources`の集合を確認すると、常に
  `{Type}.Common.g.cs`+(`{Type}.Aos.g.cs`または`{Type}.Soa.g.cs`)の2件だけが存在した)。
- SoAバックエンドで生成される`{Type}SoaGeneratedArchetype`は`IEcsArchetype<T>`を実装するため、
  `World.GetOrCreateStorage<T>()`の`Type[]`シーケンス一致によるストレージ共有を無償で
  継承する。実際に正規化後の構成が同じ`Character`/`CharacterAlias`(宣言順・型名を変えた)を
  同じ`World`上に作成し、`TryGetChunk`で取得した`ChunkView.Count`が両方とも2になる
  (互いの行が混在する)ことを`GenerateEntitySoaRuntimeTests`で確認した。
- `{Type}Store`をAoS/SoAとも`internal`にする設計を最初に試みたところ、生成コード内で
  `internal`な行構造体/アーキタイプ型を`public`な`ChunkView`メンバーのシグネチャに
  露出させる箇所でCS0051/CS0053(アクセシビリティの不整合)が実際に発生した。`{Type}Store`を
  `public`(見本と同じ)にし、`{Type}ChunkView`とその内部型は`internal`に統一することで解消した
  — この過程で、`public static Character Spawn(CharacterStore store, ...)`という見本通りの
  公開静的ファクトリを書くには`CharacterStore`自体が`public`である必要があることを実装時に
  発見した。
- 見本の`CharacterGeneratedMetadata.NormalizedSignature`(`ReadOnlySpan<string>`を返す
  式形式の`static`プロパティ、コレクション式で直接構築)は、見本を独立プロジェクトへ移して
  ビルドした際に実際にCS9203(コレクション式がスコープ外に公開される可能性がある)で
  失敗した。バッキングフィールドを介する形に最小修正して解消した。

## 意図と観測の一致
Conformance: Matches。ADR-0024に記載した意図した設計(Facade統一・コンパイル時のみの切替・
選択Backendのみ生成・Runtime分岐なし・単一Chunk方式・アーキタイプ共有・
Generation.Abstractions新設の理由)と、実際にビルド・テスト・生成コード実行で確認した挙動の間に
既知の乖離は無い。

## 残課題

- AoSバックエンドの異なる生成型間ストレージ共有は未実装。
- `[GenerateEntity]`の`UserGameProject`実利用は未追加(`Scene1.cs`との名前衝突リスクのため)。
  将来`Scene1.cs`の整理が行われた時点で追加を検討できる。
- `CSharpGameEngine.CodeAnalysis.Abstractions`の再検討トリガー条件はADR-0015の記載を継続。
- 動的Add/Remove、Archetype Migration、Query/System基盤は未実装。
- 次のマイルストーンに進む前提条件: 動的構造変更・Query/System機能・複数物理Chunkページングの
  いずれかの具体的な要件が確定すること。
