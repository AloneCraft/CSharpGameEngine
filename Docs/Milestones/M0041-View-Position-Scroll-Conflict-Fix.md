# M0041: ギズモ編集確定直後にコードエディタが無関係な位置へスクロールする不具合の追加修正

## 目的

[[M0040-Source-Marker-Rescroll-Fix]]で「Hierarchyパネル専用の古い選択を再解析着地時に参照して
いた」不具合を修正したが、実機で「直ってない」と再報告された。スクリーンショット3枚と、
ユーザーへの確認質問への回答から、M0040とは別の、より根深い原因が判明した。

## 再報告された症状

1. SM_Cube20を選択(正しくソースがマーク・スクロールされる)。
2. ギズモで移動してPositionを変更 → **マウスを離してドラッグを確定した直後、コードの数値が
   実際に書き換わるより前に**、コードエディタが無関係な位置(ファイル末尾付近)へスクロールして
   しまう。
3. 本来は、編集した数値がその場(スクロール位置を動かさず)で書き換わってほしい。

ユーザーへの確認で以下が判明した:
- 誤ったスクロールは**確定直後にすぐ**起きる(コードの値が更新されるより前)。
- このテスト中、**Hierarchyツールウィンドウは一度もクリックしていない**。

## 根本原因(消去法で特定)

2点目の確認により、M0040が修正した経路(`SceneEditorHub.HierarchySelection`由来の古い選択)は
今回の再現に一切関与していないと判明した——`HierarchySelection`は初期値`Empty`のままのはずで
ある。M0040の修正自体は別の実在するバグに対して正しかったが、**この症状の真因ではなかった**。

`SceneSourceMarkerService.Update`のスクロールゲートを再確認したところ、Move/Rotate/Scaleの
ドラッグは選択(どのノードが選ばれているか)を一切変えないため、`NodePath`(値型、
`IEquatable<NodePath>`実装済み)を比較する`SelectionChanged`判定は**理論上false**になり、
`SourceMarkerService`はこの種の編集で一切スクロールしないはずだと判明した。つまりM0040が
修正した経路も、既存の`OnSelectionChangedForHierarchy`も、単純なTransform編集ではそもそも
呼ばれても何もしない。

この消去法により、ビューのスクロール位置(トップ行)を実際に触っているコードは
`SceneWorkspaceService.ApplyTextAsync`内の`CaptureViewPositions`/`RestoreViewPositions`
**だけ**だと判明した。この機能はM0036時代、書き戻しがコミット直後に同期的に近いタイミングで
起こるという前提で設計された(「ユーザーが別の箇所を読んでいる間の編集を邪魔しない」ための
保護)。ところが[[M0038-Edit-Latency-Prediction-Layer]]で書き戻しを非同期化・背後直列化した
ことで、`CaptureViewPositions`が実際に呼ばれるのは「コミットした瞬間」ではなく「プロジェクト
全体のコンパイル取得を含む書き戻しチェーンが自分の番に到達した瞬間」になった。この間、
コードエディタのスクロール位置が選択直後の正しい位置からズレていた場合、そのズレた状態を
そのまま捕獲して書き戻し後に復元してしまう。`SourceMarkerService`は選択が変わらない限り
介入しないため、この「Top(先頭行)の保存・復元」だけが、実際に見えているスクロール位置を
編集のたびに強制的に書き換える唯一の経路として残っていた。

正確な「なぜ捕獲時点で位置がズレているのか」の一次原因(M0038の非同期化に伴うタイミング変化
そのものか、他の要因かの完全な特定)までは静的解析で断定できなかったが、この機構を通さない
限り位置が動く経路自体が存在しないため、修正対象として妥当性が高いと判断した。

## 実装したこと

`ApplyTextAsync`の位置保存・復元から**ビューポート先頭行(Top)の保存・復元を撤去**し、
**caret位置の保存・復元だけを残した**。

- caret保存・復元は維持: 「ユーザーが編集中の文字位置を、無関係なバックグラウンド書き込みで
  動かさない」という当初の目的にそのまま合致し、`SourceMarkerService`の管轄外。
- Top(先頭行スクロール)の保存・復元は撤去: スクロール位置の決定権を`SourceMarkerService.Update`
  の「選択が実際に変わったときだけスクロールする」ロジックへ完全に一本化した。これは既に
  M0032/M0040で意図されていた設計であり、`CaptureViewPositions`/`RestoreViewPositions`は
  それと競合する別経路として残っていた。

`ViewPositionSnapshot`から`Top`プロパティを削除し、`CaptureViewPositions`は`Caret`だけを
キャプチャする最小構成へ整理した。

## Evidence

`CaptureViewPositions`/`RestoreViewPositions`はVS SDK(`IVsTextManager`/`IWpfTextView`)依存の
ため既存方針どおりユニットテスト対象外。純粋ロジックの変更を伴わないため新規テストは無し。
ソリューション全体1043/1043(既存1043、テスト数増減なし、リグレッションなし)。

## 実機確認項目

| # | 確認対象 |
|---|---|
| 1 | SM_Cube20を選択 → Move/Rotate/Scaleでドラッグして確定 → コードエディタのスクロール位置が動かず、編集した数値がその場で書き換わって見える(今回の主目的) |
| 2 | 別のノードを選択し直すと、正しくそのノードの位置へスクロールする(回帰確認) |
| 3 | コードエディタで無関係な箇所を編集・閲覧している間にギズモ編集をしても、キャレット(入力位置)が勝手に動かない(caret保護機能の回帰確認) |
| 4 | Hierarchyパネルでのクリックによるマーク・スクロールは従来どおり動く(M0040の回帰確認) |
