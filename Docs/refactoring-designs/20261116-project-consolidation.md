# プロジェクトの数を減らす

## 用語

| 言葉 | 意味 |
|---|---|
| プロジェクト | `.csproj` のファイル 1 つ。組み立てると DLL か実行ファイルが 1 つできる |
| 共有プロジェクト | `.shproj` のファイル。それ自体は DLL にならず、ソースを使う側のプロジェクトへ取り込ませる |
| DLL | 組み立てた部品のファイル。ゲームや道具が読み込んで使う |
| 対象の環境 | 部品が動く .NET の種類。`net10.0`(普通の .NET)、`net10.0-windows`(Windows 専用の機能を使う)、`netstandard2.0`(古い形式。自動でコードを作る部品と Visual Studio の拡張が読めるのはこれだけ)、`net472`(Visual Studio の拡張そのもの) |
| 自動でコードを作る部品 | `CodeAnalysis`。ゲームを組み立てるときに C# のコンパイラーの中で動き、シーンや ECS のコードを作る |
| 数値の精度ごとの部品 | ゲームが選んだ数値の精度(固定小数点の桁や float/double)ごとに、ソースから作り直す部品(`Numerics`、`World`) |
| 層 | 部品の役割の段。下の層(L0)は画面の装置を直接操作し、上の層ほどゲームに近い。下の層が上の層を使ってはいけない |

## 背景

所有者の依頼(2026-11-16):「プロジェクトファイルが多すぎる。ランタイムは 1 つにまとまるだろうし、テストもまとまると思う。できるだけ少なくして」。

元の作業ツリー(枝 `refactor/project-names`)には、この方向の途中の変更が保存されずに残っている。音声の部品 `Audio` を `Core` へ、シェーダーの成果物の部品 `ShaderArtifacts` を `Contracts` へ移すもの。所有者の指示で、これを出発点として引き継ぐ。

## 現状の観察(2026-11-16、`b88ab1b7` と途中の変更)

プロジェクト 79 個と共有プロジェクト 11 個、合わせて 90 個。

| 場所 | 数 | 中身 |
|---|---|---|
| `src` | 15(途中の変更の後は 13)+ 共有 6 | エンジン本体 |
| `tests` | 23 | 試験 |
| `tools` | 21 | 道具(実行ファイル 19、DLL 2) |
| `stages` | 10 + 共有 1 | 機能ごとの確かめ用の場面 |
| `Templates`・`UserEcsProject`・`samples`・`plugins`・`packaging` | 4・1・2 + 共有 1・2 + 共有 3・1 | テンプレート、試しのゲーム、例、プラグイン、SDK の梱包 |

エンジン本体の部品が分かれている理由のうち、変えられないもの:

1. **自動でコードを作る部品(`CodeAnalysis`)は `netstandard2.0` で、ほかの DLL に頼れない。** コンパイラーの中で動くため。
2. **Visual Studio の拡張(`net472`)が読む部品は `netstandard2.0`。** `Contracts`、`SceneModel`、`ShaderGraph`(途中の変更で `ShaderArtifacts` は `Contracts` へ)。
3. **数値の精度ごとの部品は、ほかと同じ DLL に入れられない。** ゲームは精度ごとに作り直した `Numerics`・`World` を読む。同じ型が既定の精度でほかの DLL にも入っていると、型がぶつかる。
4. **`Entities` はゲームの組み立てにソースのまま取り込まれる。** 静的な ECS を作るため、生成器が同じコンパイルの中で見る必要がある(`Game.props`)。DLL にも入れると型がぶつかる。
5. **画面の装置を直接操作する部品(`Windows`)は `net10.0-windows` 専用。**
6. **素材を取り込む部品(`Import`)と作る部品(`Cooking`)は、制作のときだけ使う。** 配布物に入れない決まり(M0128 で確かめた)なので、ゲームが読む実行時の部品とは分ける。
7. **実行時の共有プロジェクト 6 個(`Runtime.*`)は、どれもゲームの組み立てにまとめて取り込まれる。** 分けておく理由は無い。

試験が分かれている理由のうち、変えられないもの: 対象の環境が 3 種類ある(`net10.0`、`net10.0-windows`、`net472`)。1 つの試験プロジェクトは 1 種類しか持てない(複数指定すると全試験が各環境で動き、Windows 専用のものが動かない)。

ほかに手間がかかるもの:
- 自動の確かめの一覧(`tools/FeatureRunner`)が、試験プロジェクトの名前とパスを 141 か所で直接使っている。
- 内部の型を試験に見せる設定(`InternalsVisibleTo`)が、試験プロジェクトの名前で 30 か所ほどある。
- 層の決まりの試験(`EngineLayerSpec`)の一部は、プロジェクトの分かれ方で層を守っている。

## 目的

- プロジェクトの数を、変えられない理由のあるものだけに減らす。
- 機能と画面の見た目を変えない(固定 7 画像の生の画素、全試験の合格を保つ)。
- 層の決まりは、プロジェクトの分かれ方の代わりに、フォルダーと名前空間を調べる試験で守る。

## 非目的

- 道具の実行ファイルをまとめること(段階 2 として別に判断する。下の「未決事項」)。
- テンプレート、試しのゲーム、例、プラグインのプロジェクト(それぞれが 1 つのゲームなので、まとめられない)。
- 機能ごとの確かめ用の場面(`stages`、各 1 つのゲームとして動く)。
- 名前空間の変更(型の名前とシーン JSON の型名は変えない)。

## 所有者の質問への答え(2026-11-16)

- **数値の精度ごとの部品は `using` で名前を変えればよいのでは:** ぶつかるのは名前だけでなく、中身の形が違う型が同じ完全な名前で 2 つあること。既定の `LogicalScalar` は `Int128` を持ち、double を選んだゲームの `LogicalScalar` は double を持つ。1 つの `Engine.dll` に入れると既定の版で固定され、ゲームは CS0433(どちらの型か分からない)になる。`extern alias` で選べても、組み立て済みの `Engine.dll` のコードは既定の版の型を受け取るので、ゲームの値を渡せない。今の `Core`・`Rendering`・`Content` は `LogicalScalar` を使っていないので、`Numerics` と `World` だけを精度ごとの部品として分ければよい。
- **ソースのまま取り込む部品は DLL にしたら動かないのか:** 動かない。`World` と `State` は partial struct で、残りを生成器がゲームのコンパイルの中で書き足す(ADR-0033)。partial は 1 回のコンパイル(1 つの DLL)の中でしか合体しないので、DLL にすると生成器が書き足す相手がゲームの中から消える。
- **画面の装置とは、Mac の試験は別のプロジェクトか:** GPU と、Windows で GPU に命令を出す Direct3D 12 のこと。Mac なら Metal を扱う部品と、`net10.0-macos` の別のプロジェクトと試験プロジェクトが要る。1.0 までは Windows と Direct3D 12 だけ(ADR-0098)。
- **取り込む部品と作る部品とは:** `Import` は glTF・FBX・PNG などのインポーター。`Cooking` は取り込んだ素材を実行時の成果物にベイクする部品(プラグインのナビメッシュや事前の割り方など)で、生成器(`CodeAnalysis`)とは別。どちらも制作のときだけ使う。

## 影響範囲

- `CSharpGameEngine.slnx`、各 `.csproj` のつながり、`build/*.props`・`*.targets`(ゲームの組み立て、数値の精度ごとの部品)、SDK の梱包(`packaging/Sdk`、`CgeEngineLibrary` の一覧)、VSIX が同梱する部品の一覧。
- `InternalsVisibleTo` の名前、`tools/FeatureRunner` の試験の名前とパス、変更から試験を選ぶ仕組み(`ChangedStageSelector`)。
- `EngineLayerSpec` などの層の試験(プロジェクトのつながりで見ていたものを、フォルダーと名前空間で見る)。
- 文書: `Architecture.md` のプロジェクト構成、AGENTS.md のソリューション登録の規則に関わる試験。

## 移行手順

各段で、組み立てと全試験と固定 7 画像を確かめてから保存する。

1. 途中の変更(`Audio`→`Core`、`ShaderArtifacts`→`Contracts`)を仕上げて保存する。
2. 共有プロジェクト `Runtime.*` 6 個を 1 個にまとめる。`World` を `Numerics` へまとめる。
3. `netstandard2.0` の部品(`SceneModel`、`ShaderGraph`)を `Contracts` へまとめる。
4. `Content`・`Rendering` を `Core` へまとめ、名前を `Engine` にする。層の試験をフォルダーと名前空間で見る形に直す。
5. `Cooking`・`Import` を `Authoring` にまとめる。配布物に制作専用の部品が入らないことを確かめる。
6. 試験を 3 個にまとめる。`InternalsVisibleTo` と自動の確かめの一覧を直す。
7. 文書を直し、全体を確かめる。

## テスト計画

- 各段: ソリューション全体の組み立て、全試験(GPU を含む)、固定 7 画像の生の画素の一致。
- 試験の件数が、まとめる前と同じであること(まとめで試験を失っていない)。
- 層の試験が、わざと違反を入れると失敗すること。
- 段 5 の後: SDK を梱包し、テンプレートのゲームを組み立てて発行し、配布物に制作専用の DLL が無いこと(M0128 と同じ確かめ)。

## リスクと対策

| リスク | 対策 |
|---|---|
| 同じ DLL に入った型の名前がぶつかる | 段ごとに組み立てて確かめる。ぶつかったら名前空間で区別する(型名は変えない) |
| 1 つにまとめた試験の中で、並行して動く試験どうしが共有の状態でぶつかる | 画面の装置を使う試験は既存の順番待ちの仕組み(`D3D12GpuCollection`)に入っている。まとめた後に全試験を 2 回流し、不安定なものを探す |
| 自動の確かめの一覧(141 か所)の書き換え漏れ | 一覧の試験(`EveryStageInputPathExists` など)で、存在しないパスを見つける |
| 数値の精度ごとの部品やゲームの組み立てが壊れる | テンプレートのゲームを SDK から組み立てる確かめを段 4・5 で行う |
