# ADR-0098 — 製品の目標、段階、妥協の範囲、後方互換性の規則

- 状態: Accepted(2026-11-15。ユーザーの依頼:「最終的に何をやろうとしているのか、ロードマップ、何を妥協するべきか、後方互換性の戦略、類似ソフト・アセットに対する優位性を決めて」。案を [目標、ロードマップ、戦略.md](../目標、ロードマップ、戦略.md) に書き、ユーザーが「確定して ADR 化」と承認した。案で仮に決めた 5 項目もそのまま確定)
- 関連: ADR-0002(ソースと成果物)、ADR-0033・ADR-0077(ゲームコードの書き方)、ADR-0051・ADR-0057(検証)、ADR-0063(正準数値と階層 World)、ADR-0065(SDK パッケージ)、ADR-0070(シーン JSON)、ADR-0079(プラグイン)、ADR-0084(対数深度)、ADR-0085(URP の 4 描画パス)、ADR-0086(全スケール物理)、ADR-0093(数値設定のビルド)
- 詳しい内容と比較表: [目標、ロードマップ、戦略.md](../目標、ロードマップ、戦略.md)

## 背景
- 2026-08-03 から 481 コミット、ADR 97 件、機能台帳 200 件まで進んだが、製品として何を目指し、どこで止め、何を捨てるかを決めた文書が無かった。
- その結果、Roadmap.md はトラックごとの機能の列になり、M0121(Deferred 系)のような大きな計画が、ゲームの要求と関係なく順番待ちに並んでいた。
- 互換性について、「旧リーダーを残さない」(Roadmap.md)と「旧版を読む」(シーン JSON v1/v2、Snapshot v1、WorldCell v1、`.cgephyscache` スキーマ 2)が混在していた。
- 制作の一巡(新規作成から配布まで)の実 Visual Studio での受け入れが、M0128 で未完了のまま残っている。

## 決定

### 1. 目標
「C# と Visual Studio だけで、テキストを正本にして、量子から銀河までの大きさの世界を決定的に動かす 3D ゲームを、Unity や UE より少ないコードで作れるエンジン」とする。判断の軸は次の 4 本の柱で、新しい作業はどれかに効くことを示す。

1. 書く量が最小(機械が決められることを書かせない)
2. テキストが正本(C#、JSON、元の素材。生成物は作り直せる。CLI だけで全工程が動く)
3. 全スケールで決定的(固定小数点、階層座標、対数深度)
4. 機械が検証できる(画面なしで実行し、判定基準で合否を出す)

第一の利用者は所有者自身。次は C# を書ける個人と小さなチームの、Windows PC 向け 3D ゲームとする。

### 2. 段階
期日ではなく出口条件で管理する。新しいマイルストーンは、冒頭にどの段階の出口条件に効くかを書く。

| 段階 | 内容 | 出口条件 |
|---|---|---|
| A 閉じる | M0128 の制作の一巡、M0114 の仕分け、M0120 のフレーム計画の移行まで、F-L8-029 | 隔離環境で VSIX 導入 → 新規作成 → 編集 → ビルド → 自己完結の配布物 → 実行が実 VS で通る。PartiallyImplemented が Implemented か理由つきの Deferred になる |
| B 1 本作る | リポジトリの外で、地表から軌道まで続く小さなゲームを作る。M0122 を前へ出す | 完成して配布した。1 つのシーンで地表の 1 mm と軌道の距離を同じ座標で扱う。再実行で状態のハッシュが一致する |
| C 公開 1.0 | UE 由来の素材の差し替え、API の凍結、互換規則の機械検査、ライセンス、NuGet と VS Marketplace への公開 | 別の PC で文書だけからテンプレートが動く。5 章の「1.0 以降」が有効になる |
| D 広げる | 実際のゲームが要求した順に足す | — |

### 3. 順序の変更
- M0121(Deferred / Deferred+ と 4 パスの選択)は段階 D へ送る。ADR-0085 の設計は取り消さず、実施の時期だけを変える。
- M0120 は L4 化とフレーム計画の移行までを段階 A に入れ、Forward / Forward+ の作り直しは段階 D へ送る。
- M0122(全スケール物理)は段階 B に入れる。M0123(物理の契約とソルバーの分離)は段階 D。
- Simulation の将来機能 25 件(F-L5-004〜031 の未実装分)は 1.0 まで着手しない。カタログの `NotImplemented` の Stage は残す。

### 4. 妥協する範囲
- 1.0 まで Windows x64 と Direct3D 12 だけ。編集は Visual Studio だけ。
- UE との見た目の一致はテンプレートの移植で打ち切る。残る差は文書に残し、閉じる作業はしない。
- 1.0 の描画は現行の 1 系統。
- 数値設定の保証を 3 段に分ける。段 1 は Q64.64 と対数深度(全 Stage、決定性、全スケール)。段 2 は Double と通常深度(ビルド、テンプレートの実行、保存の読み書き)。段 3 はそれ以外(ビルドと数値ライブラリの試験だけ。実験扱い)。
- 決定性の保証は、同じビルド、同じ数値設定、CPU の経路の中だけ。版をまたぐ再生と GPU の結果は保証しない。
- ネットワーク対戦、UI の仕組み、コードのホットリロードは 1.0 の範囲外。

妥協しないもの: 層の依存方向(L0〜L6 は Roslyn と VS SDK を参照しない)、テキスト正本と CLI だけの全工程、段 1 の決定性、未確認を成功と書かないこと、ユーザーに書かせる量を増やさないこと。

### 5. 後方互換性
1.0 までは壊してよい期間とし、1.0 以降は対象ごとに次の規則を守る。

| 対象 | 1.0 まで | 1.0 以降 |
|---|---|---|
| A. ユーザーが書いた資料(シーン JSON、`.cgeasset`、`.cgepreview`、サイドカー、シェーダー グラフ、csproj の設定、プラグインのマニフェスト) | 壊してよい。変換ツールを同じ変更で出す。読み手は最新版だけ | 1.0 以降のすべての版から最新へ変換を連鎖で保つ。読み手は最新版だけ |
| B. ユーザーの C#(Component、System の引数の規則、属性、生成 API、診断 ID) | 壊してよい。黙って意味を変えない。消した書き方は診断で知らせる | メジャー版でだけ壊す。1 つ前のマイナー版で警告し、アナライザーのコード修正を付ける |
| C. 作り直せる生成物(シェーダー、モデル、`.cgenav`、`.cgefracture`、`.cgesdf`、キャッシュ) | 互換なし。版か指紋が合わなければ拒否して作り直す | 同じ |
| D. 遊ぶ人のデータ(Snapshot) | 保証しない | 容器の形式は 1.0 以降のすべての版を読む。Component の形の変更はゲームが移行を宣言する |
| E. 決定性に縛られた記録(物理キャッシュの再生、リプレイ) | 互換なし | エンジンの版と数値設定が一致するときだけ再生する |
| F. 道具の間の通信(プレビューのプロトコル、ブリッジの DTO) | VSIX は同梱した SDK と同じ版だけ | VSIX は同じマイナー版の SDK |
| G. エンジン内部の API | 互換なし | 互換なし |
| H. 土台(.NET、VS、Windows) | 最新の LTS の .NET と対応する VS の 1 世代 | 同じ。LTS が替わるメジャー版で切り替える |

共通の規則:
1. 壊すときは止める。旧形式を黙って読まず、直し方を書いたエラーにする。
2. 変換は CLI が行う 1 方向の処理とし、旧版を読む経路をランタイムと生成器に残さない。
3. A と D は各版の見本を試験の入力に残す(1.0 以降)。
4. 最初の公開まで、製品の版は 0.1.0 に固定する(2026-11-15、所有者の指示「まだリリースしていないので 0.1.0 にすべき」)。公開前は互換を約束しないので、壊す変更でも版を上げない。
   - SDK パッケージは `0.1.0-dev.N` とし、中身を変えるたびに N を上げる。NuGet は一度展開した版を使い続け、キャッシュには開発初期の素の 0.1.0〜0.1.25 が残っているため、素の 0.1.0 は使わない。プレリリースの番号は正式版の 0.1.0 より前に並ぶ。
   - VSIX の版は数字しか使えず、更新には番号の増加が要るので `0.1.0.N` とする。
   - 最初の公開で SDK を `0.1.0`、VSIX を `0.1.0.N` にする。公開した後は、A か B を壊したらマイナーを上げ、`CHANGELOG.md` に移行の手順を書く。
5. 互換のために残した名前(例: シーン JSON のための名前空間 `CSharpGameEngine.Runtime.Windows`)は、1.0 の前に一括変換で消す。

今ある旧版の読み手(シーン JSON v1/v2、Snapshot v1、WorldCell v1、`.cgephyscache` スキーマ 2・3)は、規則 2 に合わせて変換ツールへ移し、読み手から削る。→ 2026-11-15 に実施した([設計と記録](../refactoring-designs/20261115-legacy-reader-removal.md))。シーン JSON の旧版は `SceneJson.Cli upgrade` だけが読む(ナビメッシュの Cook も版 3 だけ)。Snapshot・WorldCell・物理キャッシュ・`.cgefracture` の旧版は変換せず拒否する(D・C・E)。ビルドが利用者のメタデータを黙って書き換えていた glTF の旧インポーター名(IMP008)も、明示の変換だけに改めた。

### 6. 公開と素材
- 公開する。段階 C で NuGet と VS Marketplace に出す。
- テンプレートの UE 由来の素材(`THIRD_PARTY_NOTICES.md`)は、段階 C で自作か条件が明確なものへ差し替える。それまで SDK と VSIX を公開の場所へ出さない。UE の EULA の判断は所有者が行う。
- エンジンのライセンスは段階 C で決める(現在リポジトリに LICENSE は無い)。

## 採らなかった案
- **トラックごとに全部を完成させてから製品にする(現行の Roadmap.md の進め方)**: 完了条件が無く、ゲームが 1 本も出来ないまま機能が増える。
- **今から互換を保つ**: 外部の利用者がいない段階で、旧版の読み手と並行 API の維持費を払うことになる。
- **互換を一切保たない(1.0 以降も)**: 公開した後、ユーザーのシーンとセーブが版を上げるたびに読めなくなる。
- **M0121 を予定どおり先に進める**: 4 パスの一致検証は高価で、段階 B のゲームに要らない。
- **独立エディターを作る**: Visual Studio の中で完結することが、Unity・UE・Godot・Stride に対する差の一つで、費用もエンジン本体へ回せる。

## 影響
- Roadmap.md はこの ADR と戦略文書の下位になる。機能の計画は Roadmap.md、段階と規則はこの ADR が正本。
- M0121 と M0123(物理の分離)の状態は「計画(段階 D)」になる。M0122 は段階 B の最初の作業になる。
- 数値設定の段 2・段 3 の Stage は、段 1 と同じ保証を要求しない。Numeric-Configuration.md の検証範囲の書き方は、次にその文書を触るときに段の名前で揃える。
- 段階 C までに、旧版の読み手を変換ツールへ移す作業が発生する。

## 検証
文書だけの決定で、コードは変えていない。次の段階で確かめる。
- 段階 A の出口条件: 隔離環境での実 VS の一巡(M0128 の記録)。
- 段階 B: ゲームでの状態ハッシュの一致、他のエンジンとの書く量と速さの比較(戦略文書 6.3 の仮説)。
- 段階 C: 互換規則の機械検査(公開 API の差分、変換の連鎖の試験)。

## 関連する機能
特定の Feature ID は変えない。段階の割り当ては M0120・M0121・M0122・M0123 の各文書に書く。
