# ADR-0079 — プラグインとアセット: UE と同じようにユーザーが機能とデータを足せるようにする
- 状態: Accepted(2026-10-22。ユーザーの依頼:「こういう拡張機能はUEのプラグインやアセット開発と同じようにユーザーが作れるようにして」「プラグインとアセットの違いも明確にして」「機能追加の方法も考えて」「生成ルールをユーザーが追加するかDLLかコード追加か」)
- 関連: ADR-0065(ゲームプロジェクトの取り込み規約と SDK パッケージ)、ADR-0077(ゲームコードの書き方)、ADR-0078(UE テンプレートの完全移植)、ADR-0019・ADR-0020(別プロセスへの統一)、ADR-0033(Archetype)、M0103

## 背景
- ADR-0078 で、車両(Chaos Vehicle 相当)、ナビメッシュ、破壊を足す。これをエンジンの中に作り込むと、ユーザーは同じ形の機能を自分では足せない。
- 調べた事実(2026-10-22):
  - プラグインやモジュールの仕組みは無い。`build/CSharpGameEngine.Game.props` が Runtime.* の `.projitems` をソースとして取り込み、10 個の DLL を参照する、固定の構成。
  - System と、`World`・`State`・`Entity` を名指しするコードは、ソースでしか足せない。理由は 3 つ。
    - `World` と `State` は partial 型で、生成器(`GameSystemGenerator`)が同じコンパイルの中で完成させる。Entities のソースはゲームごとにコンパイルされ、型の同一性はゲームごとに違う。
    - 生成器は `ISystem` をソースの構文からだけ探す(`CreateSyntaxProvider`)。
    - Archetype と Component の番号は、ゲームごとに 1 つの空間で振る(`GameSystemIndexAssigner`)。
  - Component の構造体とサービスの型は DLL に置ける(例: `Camera` は `CSharpGameEngine.Windows.dll`)。
  - サービスは `EngineHost` のプロパティの型だけ(`GameSystemAnalyzer`)。Component は全部で 128 種類まで(SYSGEN026)で、UserEcsProject だけで 58 を使う。
  - アセットはデータだけのファイルで、`Assets/` をそのままコピーしてパスで読む。シーンは C# にコンパイルする。ユーザーが定義するデータの型は無い。

## 決定

### 1. プラグインとアセットの違い
| | プラグイン | アセット |
|---|---|---|
| 何か | 機能の単位。新しい「種類」と「振る舞い」を足す。Component、System、サービス、イベント、データアセットの型、取り込みとベイクの処理、エディタの表示情報。 | データの 1 つの実体。エンジンかプラグインが定義した型の値を持つ。メッシュ、テクスチャ、音、シーン、シェーダーグラフ、データアセット、ナビメッシュ、破砕資産。 |
| コード | 持つ(C# のソースと DLL) | 持たない。Blueprint に当たる「処理を持つアセット」は作らない。処理は C# の System に書く。 |
| 作る人 | プログラマ | アーティストとデザイナー(Designer で編集する。インスペクターはスキーマから作る) |
| UE で言うと | `.uplugin` とそのモジュール | `.uasset`(`UDataAsset` を含む) |
| 中身 | マニフェスト `<名前>.cgeplugin`、Runtime モジュール(ソース)、Library モジュール(DLL)、Cook モジュール(DLL)、`Assets/` と `Scenes/` | ファイル 1 つ(と `.meta`) |

判断の基準: 毎フレーム動くもの、振る舞いを決めるものはコード(ゲームかプラグイン)。人が調整する値はアセット。プラグインはアセットを同梱できるが、アセットはプラグインを含まない。

### 2. 機能を足す 3 つの場所
UE の Game モジュール、Project プラグイン、Engine と Fab のプラグインに対応する。
1. ゲームのコード: プロジェクトに直接書く(今のまま)。
2. プロジェクトのプラグイン: `Plugins/<名前>/<名前>.cgeplugin` のフォルダ。Game.props が見つけて有効にする。
3. 配布するプラグイン:
   - エンジンのプラグインはリポジトリの `plugins/` に置き、SDK パッケージの `plugins/` に入れる。版は SDK と同じ(ADR-0065 の 1 パッケージの方針のまま)。
   - 他の人のプラグインは自分の NuGet パッケージにする。パッケージの `build/<id>.props` が自分を登録する。
   - エンジンのプラグインは、csproj の `<CgePlugin Include="<名前>" />` で有効にする。テンプレートは必要なものを書いておく。

### 3. 足し方(「生成ルールか、DLL か、コードか」)
| 足したいもの | 方法 | 理由 |
|---|---|---|
| Component、System、イベント、`[InputActions]` | ソースのコード。プラグインの Runtime モジュールに置き、ゲームと一緒にコンパイルする。 | 背景の 3 つの理由。エンジン自身の Runtime.* と同じ形。 |
| サービス | クラスに `[EngineService]` を付ける。生成器が見つけ、System の引数に渡す。 | `EngineHost` のプロパティだけでは、プラグインがサービスを足せない。 |
| 重い計算、ネイティブ、外部ライブラリ、隠したい実装 | DLL(Library モジュール)。`World`・`State`・`Entity`・`ISystem` を名指ししない。 | DLL にできるのはここまで。Runtime のソースを薄くして、本体を DLL に置ける。 |
| 新しいデータの種類 | 型に `[DataAsset]` を付ける(コード)。値は `.cgeasset` のアセット(データ)。 | シーンと同じく、生成器が C# にコンパイルして `Assets.*` の型つきの参照にする。実行時の読み込みもリフレクションも要らない。 |
| 新しい取り込み形式とベイク | DLL(Cook モジュール)で `IAssetCooker` を実装する。ビルドとエディタが別のプロセスで動かす。 | ADR-0019・0020 の「別プロセスで統一」に合わせる。VS のプロセスにユーザーの DLL を読ませない。 |
| エディタの拡張 | 宣言だけ(アイコン、表示順、インスペクターの属性)。独自の WPF パネルは作らない(v1)。 | VSIX は net472 で VS のプロセスの中にある。 |
| C# のコード生成ルール(Roslyn の生成器) | ユーザーは足さない(v1)。エンジンの生成器 1 つを、属性とマニフェストで広げる。 | Roslyn の生成器どうしは互いの出力を見られない。ユーザーの生成器が作った Component や System は、`World` と Archetype を作るエンジンの生成器から見えず、整合が壊れる。順序と診断の決定性も守れない。 |
| 描画のパスと計算シェーダー | 足せない(今のまま)。マテリアルのシェーダーグラフはアセットとして同梱できる。 | 描画契約(`stage-v*`)はエンジンが持つ。 |

### 4. サービス(`[EngineService]`)
- `[EngineService]` を付けた参照型のクラスを、System の引数に書けばサービスとして渡す。
- 生成器は `GeneratedSystemSet` にフィールドを置き、最初に使うときに作る。コンストラクターは引数なし、または `EngineHost` を 1 つ取るもの。
- `IDisposable` なら、`Shutdown` で作った逆の順に破棄する。
- `EngineHost` のプロパティのサービス(`Audio` など)は、今のまま。ネイティブの資源を持つエンジンのサービスはここに残る。

### 5. Component の上限
- プラグインはゲームと同じ番号の空間を使うので、上限を 128 から 512 に上げる。マスクは 64 ビットの語を必要な数だけ並べる。
- 128 種類以下では、生成するコードを今と同じにする(1 語と 2 語の境界の性能の証拠 F-L7-032 を変えないため)。

### 6. 名前の衝突
- 生成する World のフィールド名は、型の単純名から作る。2 つのプラグインが同じ単純名の Component を持つと、今は SYSGEN020 になる。単純名がぶつかる型だけ、名前空間を含めた名前にする。

### 7. 実装の形(M0103 で決めたこと)
- 取り込み:
  - 後から読む `build/CSharpGameEngine.Game.targets` が、プロジェクトの `Plugins/*/*.plugin.props` とエンジンの `plugins/*/*.plugin.props` を読む。後から読むのは、Game.props はプロジェクトファイルより先に読まれ、csproj の `CgePlugins` が見えないため。
  - プラグインの形は `<名前>.plugin.props`(有効かを決める)と `<名前>.plugin.items`(項目)に分ける。MSBuild は項目をすべてのプロパティの後で評価するので、プラグインごとに上書きするプロパティで項目に条件を付けると、最後のプラグインの値しか効かない。`Import` の条件は順に評価される。
  - 有効かの判定(プロパティ 3 行)は、各プラグインの `.plugin.props` に書く。共通のファイルにすると、MSBuild は同じファイルを 1 回しか取り込まないので(MSB4011)、最初のプラグインにしか効かない(M0103 の検証で起きた)。
- アセット: プラグインのアセットは、実行時に `Plugins/<名前>/Assets/…` に置き、カタログは `Assets.Plugins.<名前>.*` にする。プロジェクトのプラグインはプロジェクト相対のパスがそのままこの形になるので、3 つの置き場所で同じ形にそろえた。
- データアセット: 文書はシーンの Component 1 つと同じ形にし、シーンの値の解析(`SceneJsonSceneAnalyzer`)をそのまま使う。値の規則がシーンとずれないようにするため。
- Library モジュール: DLL は `[assembly: PluginLibrary]` で名乗る。スキーマとパレットは、名前が `CSharpGameEngine` で始まる DLL に加えて、これを見る。
- Cook モジュール: 契約は `CSharpGameEngine.Cooking`(`IAssetCooker`)。`CSharpGameEngine.Cook.Cli` が専用の AssemblyLoadContext で読む。出力フォルダの外へ書くことと、決定的でないこと(`--verify`)を拒否する。
- 生成器へ渡すフォルダ: MSBuild のプロパティは .editorconfig を通って生成器に渡り、その読み取りは値の `#` と `;` から後ろを捨てる。プラグインの根は `|` で区切り、プロジェクトとプラグインのフォルダは `#`→`?h`、`;`→`?s` に書き換えて渡す(`CgeProjectDirectory`、`CgePluginRootsEncoded`)。これで、ADR-0070 から続いていた「`#` を含むフォルダのゲームはシーンとカタログが無しにビルドされる」問題も直る。
- エンジンの版: `build/CSharpGameEngine.Version.props` の `CgeEngineVersion` 1 か所にする。SDK パッケージの版と、PLUGIN005 の判定に使う。
- 最初のエンジンのプラグイン: Vehicles(`plugins/CSharpGameEngine.Vehicles`)。M0101 段階 9 の簡易の車両を `Runtime.Character` から移し、名前空間を `CSharpGameEngine.Vehicles` にした。M0109 で中身を Chaos 相当に書き直し、データアセットの実例 `VehicleSetup` を持つ。2 つ目は Navigation(`plugins/CSharpGameEngine.Navigation`。M0106)で、最初の実際の Cook モジュール(ビルド中の自動実行と VSIX のボタンつき)を持つ。

## 結果
- エンジンの新しい機能(車両、ナビメッシュ、破壊)は、ユーザーと同じ形のプラグインとして作る。エンジンが自分で使うので、仕組みの抜けがすぐ分かる。
- シーンの型名 `CSharpGameEngine.Runtime.Character.Vehicle`(と `VehicleState`、`VehicleIntent`)は `CSharpGameEngine.Vehicles.*` に変わった。リポジトリのシーンは書き換えた。
- ADR-0081 / F-L8-035 でデータアセットの Inspector 編集と提供元付きアセット一覧を追加した(実機検証と取り込み統合は M0123)。残るもの: NuGet のプラグインの Library の DLL を実行時のプレビューが確実に読むこと(読み込まれたアセンブリだけを探すため)。
- System を DLL だけで配ることはできない。配る人がソースを隠したいときは、Library の DLL に本体を置く。
- プラグインの Runtime のソースは SDK の版に結び付く(生成器がその版の形でコードを出すため)。マニフェストに対応する版の範囲を書き、合わなければ診断を出す。
